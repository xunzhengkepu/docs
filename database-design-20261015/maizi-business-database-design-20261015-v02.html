可以精简，但要按业务边界合并

10 月 7 日方案已有 18 张表；10 月 9 日又设计了版本、审批、人工校对等对象。这些对象不应各自再建一套主记录。本版将两套设计合成一个模型，并纳入这次云盘核对暴露出的跨目录、旧版审批和历史缺证据问题。

推荐：8 张业务表 + 9 张支撑表，共 17 张。不是以表数最少为目标；重点是作品只建档一次、正式决定只保存一次、页面进度只有一个计算入口。

表数口径与旧 18 表设计一致：不包括沿用的登录账号、会话、系统级安全审计和通知设施。它们仍然需要，只是不在本次业务重构中重建。未来若自动向员工发提醒，必须接入已有可靠发送队列或另建 outbox；那时总数会增加。

可以合并

  • 员工、医生、企业联系人 Profile → 一个人员表。
  • 作品历史、任务历史、人工审核和校对决定 → 一个正式事件表。
  • Word 版本、原片、成片版本 → 一套文件与作品关联结构。
  • 普通阶段待办 → 查询视图，不再复制作品状态。

必须保留独立边界

  • 人员与账号：改昵称不改变人员身份。
  • 合作关系与作品：停新稿仍可继续已有剪辑。
  • 作品与文件：一作品多文件，一文件可复用。
  • 原消息与分析：事实不被模型覆盖。
  • 实际发布与生产进度：历史缺证据时仍能记录真实发布。

业务进度、证据完整度分别展示

页面不能只用一个“转换状态”字段涵盖全部情况。建议每个作品固定显示下面五项，均由正式事实及来源覆盖计算。

页面栏位示例依据
业务阶段待成片提交 / 待医生审片 / 待发布 / 已发布由正式事件和发布事实重建
审核状态v2 企业通过、医生待审；或版本不明具体文件关联 + 角色 + 轮次，不是作品上一个 approved 布尔值
交付与归档已交片、终版位置待核对；或已交付且可访问交付对象与时间独立于目录位置

阶段保留“正在等待什么”的含义

文案提交 → 文案审核 → 收片/补录 → 素材质检 → 成片提交 → 成片审核/返工 → 待发布/已排期 → 已发布。不同角色的审核门槛单独判断，暂停/取消另列，不压进这条线性顺序。

沿用已讨论的默认路线：科普需要医生审核；患教文案按医生→企业、成片按企业→医生。项目可配置所需角色与顺序；本次不擅自把串行规则改成并行。只有另行确认的项目政策才允许并行，所有要求仍须针对同一版本满足。

返工不是错误的“状态倒退”。新内容版本或明确重开审核会开启新轮次。旧轮次批准保留，但不授权新内容；存在冲突时显示阻塞原因。最新状态是事实投影，不能用单调递增的状态序号阻止正常返工。

审批、交付、归档、发布四件事分开

审片通过表示某版本满足某审核门槛；交付表示该版本交给了约定接收方；归档表示规定位置可访问；发布表示平台已发出。delivered 事件至少包含接收方、文件关联、交付方式与时间；历史版本不明确时只保留作品级交片事实，并标注版本未知。

新业务只有确切版本完成规定审核与交付，才能显示“终版交付完成”。历史平台发布可以独立确认，缺失的审核/终版证据不能凭空补齐。

产量、比例和期限

  • 一作品发两个平台：产量为 1，平台发布条数为 2。科普/患教比例采用已确认匹配且已发布的作品数；未匹配、类型未知记录单列，并标统计覆盖率，不能静默丢掉。
  • 补稿建议先扣除已有在制内容；暂停新增发稿只影响当前合作关系，不拦截已有素材交付。
  • 剪辑期限从确认素材收齐且可用开始，按两个工作日计算。默认北京时区、周一至周五；周五 15:30 到下周二 15:30。周末收齐以其后两个工作日计，保留同一时刻。节假日/调休仅按已确认覆盖配置；不是简单加 48 小时。
  • 在素材确认事件里冻结规则版本、起算时间和计算出的截止时间；补录、暂停等是否延后需显式决定，不因重新同步而重置。
  • 排期与实际发布时间分别保存。批准后尚未确认档期，列“待补档期”，不编造统一发布时间。

  • 唯一来源键为 provider + namespace + object_id + revision_key；重命名、移动不产生新内容版本。
  • 修改内容必须登记新版本。无可靠修订号时保留“暂定版本”，不能用当前文件冒充历史审片版。
  • 哈希不做全局唯一：相同内容可以有多个存储副本；不同剪辑内容也不会因为名字一样而合并。
  • 没有可靠版本历史的云盘接入，需验证不可覆盖命名或受控快照机制后才能保证审核回放。

字段/字段组用途

工程约束：不能靠页面约定

数据库与业务事务共同保证

  1. 跨对象归属一致。事件指向的文件关联必须属于其 work_id；发布的确切版本必须属于已匹配作品；任务关联作品与合作关系不能冲突。用外键、必要的复合外键或约束触发器落实，不只在前端校验。
  2. 审核是版本级事实。批准事件必须有已确认的 work_asset、可靠版本身份、明确 reviewer、review_gate 与 review_round。正文“可以”但版本不明只生成候选。角色授权与素材身份一并验证。
  3. 正式事实只追加。版本、审批、交付不能原地覆盖；误判用更正/撤销事件。业务可变快照及当前状态只能由同一事务下的服务入口更新。
  4. 根对象受约束。events 三个根外键恰有一个非空；只有 work 根可携带作品文件和发布子目标。任务核对接受后，先写 task 根的人工决定，再写由该决定触发的 work 根事实。
  5. 并发与幂等。读取作品 lock_version → 校验审核轮次/现选版本 → 写正式事件和消息证据 → 更新作品投影与 lock_version → 提交。版本条件不匹配则冲突重试，不能静默覆盖。
  6. 重算可解释。保存事件序列、业务时间、规则版本；迟到消息或撤销事件触发相关作品重算。事件到达顺序不必等于业务发生顺序，冲突不采用简单最后写入胜出。
  7. 源数据水位可审计。批次成功才更新 sync_state；候选处理失败不回滚已保存的原消息，重试仍幂等。聊天、云盘、发布数据分别展示覆盖时间和范围。

审批查询视图替代审批重复表

current_reviews(work_id, work_asset_id, gate, round)
  = 当前有效轮次中未撤销、未被明确更正的正式审核事件
  = 有冲突 → conflict；有修改要求 → changes_requested；符合门槛 → approved

work_queue
  = 作品当前版本 + 已满足门槛 + 阻塞项 + 当前责任人 + 截止时间
  ≠ 在每次阶段切换时复制一行 tasks

delivery_overview
  = 业务阶段 + 版本级审核 + 交付记录 + 云盘归档可访问性 + 数据覆盖

cooperation_health
  = 已发布作品数 + 在制内容 + 新稿暂停决定 + 数据统计覆盖率

视图可以先直接查询；出现性能瓶颈再加可重建投影。本版不是要求全系统做事件溯源：只有作品阶段、审核和可追责操作需要从事件重建；账号、消息、文件索引和发布事实仍是普通关系数据。

查询与索引优先级

优先为消息 (conversation_id, sent_at, id)、事件各根对象与序列、work_assets(work_id, role, variant)、work_assets(asset_id)、事件的 work_asset_id + review_gate + review_round、作品合作关系/阶段、任务责任人/状态/截止时间建索引。发布和来源幂等键建唯一约束。不要给每个 JSON 属性先建索引。

沿用身份系统，明确业务权限

现有登录账号映射到 people；员工只能访问已授权合作关系/作品及相应必要证据，主管按已有规则查看和调整。新分配只扩展明确范围，不因为在同群就开放所有聊天。云盘授权信息留在密钥配置，数据库只存稳定资源标识；访问链接在授权后按需生成。

同一原片用于两个作品两个确认关联，可分别推进1 个 asset + 2 个 work_assets原片数量不能直接计作交付条数。
v1 通过后上传 v2v1 的审核历史保留；v2 待审新 asset/link + 新一轮审核事件旧审批不迁移到新内容。

有“已交片”聊天，云盘未找到交片事实可确认，归档位置待核对版本未知的交片事件 + 待核对清单不能判未剪辑，也不能判已审通过。
有终版文件，无明确医生回复文件存在可确认，医生审批未知asset/link；无批准事件不把“终版.mp4”当批准。
医生通过，企业仍有修改意见尚未满足所需审核；需修改/处理冲突同版本分审核门槛记录 events不能让一句医生通过覆盖企业意见。
已有平台链接，历史审片记录缺失实际发布可确认；审片历史缺失publications；精确 work_asset 可空不能补造批准事件，也不能否认已发生发布。

医生在项目 A 停新增发稿只停止该合作关系的新稿engagements + events项目 B 和 A 已有剪辑继续。
云盘权限不足或同步中断覆盖范围不完整，状态可能过期sync_state.coverage + covered_through不能把扫描未见当文件删除或业务未完成。
AI 重跑把已确认作品改成另一个候选仍保留人工确认，新的冲突进入核对message_analysis + events规则/模型无权覆盖人工决定。

一个作品的最小完整例子

ENG-001：医生 A × 项目 P，默认运营 / 文案 / 剪辑已确认
WORK-001：一篇患教稿，作品编号不随标题变化

文件：文案 v1；原片 A / B；审片 v1；返工 v2
关联：上述各文件分别关联 WORK-001；原片 A 也可用于另一作品
事件：文案医生通过 → 文案企业通过 → 素材收齐可用
      → 审片 v1 企业要求修改 → v2 企业通过 → v2 医生通过
      → v2 交付 → 约定排期 → 平台实际发布
证据：每次审核绑定确切文件关联和所需聊天上下文

结果：1 个作品，多个文件版本，多次不可覆盖的历史决定，1 条实际发布。
      如再发一个平台，仅增加发布记录，不新增作品。
      如果只找到 v1 的“可以”，不能让 v2 自动通过。

落地顺序：先统一身份与事实，再换状态入口

  1. 盘点与映射。核实实际运行的 SQLite/其他存储和写入服务。旧 PostgreSQL 方案已归档，不能把设计图当作现有生产结构。冻结一份只读快照与来源 ID 映射。
  2. 建并行模型。先导入人员、账号、会话、消息、项目、合作关系和作品；保持旧服务运行。按来源键幂等，保留未知身份、缺失群和重复候选。
  3. 接文件与版本。扫描授权范围的云盘元数据、保留稳定对象 ID。核实 API 是否返回可靠修订标识、移动/覆盖语义及目录权限；未核实的版本标 provisional。先匹配新业务，再选择性补历史。
  4. 迁移正式决定。旧 task_events/work_events 转成 events，已有明确审核绑定到可证实的版本；无法确定的只保留旧状态来源与待核对信息。历史“已交片”“已发布”不能倒推完整审批链。
  5. 双读对照。比较作品数、发布作品数/帖子数、身份关联、人工决定、待回复、期限和云盘覆盖；把差异落清单。两次重跑不得多出作品、文件关联或审批。
  6. 按模块切换唯一写入口。先只读工作台，再人工确认与任务，再自动事实规则。切换前建立数据库约束、权限、并发冲突和备份恢复验证；旧库保持可回退读取。绝不一边让新旧服务各自修改同一状态而无同步协议。
建议第一阶段交付：一个作品详情页能看到稿件、所有已关联文件、版本审批、交付与发布证据；一个待核对页能清楚解释“为什么不知道”。先解决业务可追溯，再扩大自动推进范围。

现在不需要的扩展

不提前建立通用流程引擎、任意角色权限编辑器、剪辑工程逐帧素材血缘、全量视频转写、企业 CRM、历史播放量时序库。多人同岗协作、独立审核工作流或多个存储位置统一内容寻址出现真实需求时，再拆对应表；既有业务事实不丢弃。
