原清单需要收回或降级的建议

  1. P02：不强制建立视频替换链。逐句补录和替换关系主要服务剪辑，不应成为状态机的必要条件。与现有“视频之间不关联”设计保持一致。
  2. P03：不直接升级为复杂的素材多对多模型。现有一个任务、多份视频和资料已能覆盖不少情况，先避免按文件数建任务。
  3. 员工标准话术只是辅助。优先依靠文案、视频内容与上下文匹配，不把识别不足都转为要求员工写全标题、版本、用途。

会议中明确的入口调整

01:04:35—01:05:52：从文案出现开始自动跟踪，初始进入“文案待医生确认”。暂不根据群里的模糊需求自动生成“待写稿／文案中”任务，旧记录及其他业务入口另行保留。

新建前应有文案依据、真实标题、明确医生、来源消息与发送者，并检查是否已有同一作品。修订或重发优先归入已有任务。缺信息时等待后文或材料处理完成，不编标题，不先建空任务。

01:02:19—01:06:48：必要字段由程序硬性检查。10句话是上下文窗口的初始设想，不是不可调整的业务规则；明确引用和作品历史不应被窗口截断。“等待后文”属于处理状态，不必增加到任务进度标签中。

不能直接照搬的两条硬规则

  • 短于2分半的视频全部忽略：可能漏掉短成片、分段录制和补录。短素材不独立建任务，有明确关联时仍可挂到已有任务。700—800字也宜作为筛选线索，而不是唯一文案门槛。
  • OK总是确认上一条：单一对象可简化，多对象仍可能选错。建议引用优先、单一当前待审对象优先；多对象歧义保留，暂不自动群内追问。这是实现建议，不冒充会议已经逐条通过的细则。

“中间聊天都叫修改中”应理解为不追踪琐碎操作，不应让收到、感谢和闲聊触发状态倒退。

建议保留的主线

正式文案出现 → 核对必要信息并匹配已有任务 → 文案待医生确认 → 按作品类型完成文案确认 → 待录制 → 原片归属与交接明确 → 待剪辑 → 成片完成并进入对应确认阶段 → 待发布 → 已定时／已发布。

明确开剪、返工时记录对应状态；缺失中间消息时不编造过程。这次会议没有明确推翻科普与患教的审核顺序。状态事务、来源历史、幂等和人工纠正仍保留。
