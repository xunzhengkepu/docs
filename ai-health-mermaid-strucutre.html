体检报告 AI 助手 · 生产架构 · 2026

从一张体检 PDF 到一段语音解读

当前生产环境的真实链路。编排主干是 n8n cloud（health-assistant.app.n8n.cloud），它串起 RPA 网关（阿里云 ECS）、腾讯云三个独立 SCF（ai_health_report_assistant、recommendation_service、audio_analyzation）、第三方本地部署的 TTS，以及人民健康侧的服务器与小程序。意图识别在 ai_health_report_assistant 进程内直连 DeepSeek 完成；推荐系统是独立的 recommendation_service。

微信入口 / RPA 网关（阿里云 ECS） n8n 编排主干 腾讯云 SCF / LLM 厂商 人民健康（外部合作方）

总览：五段合成的完整链路

/api/audio/play_url 只签发预签名URL，不经手音频字节；小程序拿到URL后直连COS取音频播放。带圈数字为总览专属编号，与各分段图自身编号不是同一套。

第一段：消息进来，n8n 判断意图

n8n 画布上的 intent-recognition 节点打到 ai_health_report_assistant 自己的 /intent_recognition，内部调 DeepSeek 判断意图。图上 image/pdf 是并行简化画法——实际上图片消息会先累积，要等用户发"完成"或 20 秒空闲才合并成一份 PDF 再往下走。带圈数字对应下方「链路时间线」。

第二段：解读报告并合成语音

口播生成主模型失败时会降级到一个可配置的备用模型（LAYER3_FALLBACK_*，默认还是另一个DeepSeek模型，详见「/analyze 内部五步流水线」）；推荐画像通过一次 POST /snapshot 调用独立的 recommendation_service。SCF 只产文字口播稿；音频是 TTS 服务自己写进 COS 的。

第三段：送达用户并在小程序里播放

回调其实有两条分支：is_analytic_audio=true 才走图上这条人民健康握手+小程序播放的路；为 false 时会直接从 COS 下载 mp3 当文件发给用户，不经过人民健康。/api/audio/play_url 只负责用AES解开token、查ai_response表拿cos_key、签发一个1小时有效的预签名URL——它本身不经手音频字节。小程序拿到预签名URL后直连COS取音频播放，跟 SCF 无关。

/analyze 内部五步流水线

第④步「推荐快照」是对独立 recommendation_service 的一次 HTTP 调用（recommendation_client.py）；第⑤步口播生成主模型失败时会降级到备用模型（默认还是另一个DeepSeek模型，非Gemini）。推荐快照以 Layer3 curate 的结果为输入，跑在口播文案生成之前。

30天视频推荐子系统

问题档案匹配、30天排期、到期任务、视频目录同步都在独立的 recommendation_service（腾讯云 ap-beijing SCF）里；RPA 只用 recommendation_client.py 发 HTTP 请求，不直接连 COS 做排期。这里的 MySQL 跟 RPA / audio_analyzation 是同一个 Tencent CDB 实例，不是各自独立的库。RPA 仓库里还留着一个 catalog_sync.py，现在只是转发到这里 /catalog/sync 的小工具。报告解读完成后自动排期，此后每天推一条健康教育视频。

附：wellness-circle-third（视频上传入库人民健康）

本地视频上传人民健康(RMJK)的工具（README 自称 rmjk-video-uploader），部署在人民健康侧机器上，纯 Python（FastAPI/CLI，不是SCF）。封面图不是从数据库读的——本地有 cover_file 就用它，没有就 ffmpeg 现抽视频首帧裁成封面/分享图。PersistStage 建库时只写人民健康的 MySQL，"我方"的 videos 镜像表是 sync_videos.py（每天06:00）或 /api/sync 单向从人民健康拉回来的。这张"我方" videos 表和 recommendation_service 自己的 catalog_sync.py 是两条独立的同步管道，存在数据漂移的风险。

组件说明

入口

StarBot 桌面机器人

第三方企微自动化产品，捕获企业微信消息事件（文本/图片/文件/语音），非浏览器自动化。RPA 通过本机 HTTP 调它发消息。

localhost:10001 · /api/processor
网关

RPA 网关（阿里云 ECS）

转发消息给 n8n、接收结果回调、生成 AES token 并与人民健康握手。30 天视频推荐的排期与匹配在 recommendation_service，RPA 只负责按需调用与发消息；仓库里还留着一个 catalog_sync.py，现在只是转发 /catalog/sync 的小工具。

n8n cloud（生产主干）

整条链路的编排者：记录用户 → 按 msg_type 分五路（语音与兜底直接回话术结束）→ 意图识别 → 按 intent 分三条支路（报告解读 / 婉拒咨询 / 闲聊）→ 调 TTS → 回调 RPA。图中 n8n 节点名与线上画布保持一致，方便对照。

Tencent COS

原始 PDF、各层产物（profile / coverage / script）、TTS 音频的共享存储层。

{wechat_id}/output/{task_id}_*.json
核心

ai_health_report_assistant

被 n8n 以 /analyze 调用，传入 cos_key；也承担 /intent_recognition（进程内 DeepSeek 判断意图）。内部四步：识别 → 规则引擎 → 结构化精简 → 口播 LLM；推荐快照是对 recommendation_service 的一次 HTTP 调用。返回 script 与 layer3_curated，本身不产音频。

ap-beijing · POST /analyze
音频分发

audio_analyzation（audio scf）

小程序侧的音频出口：用与 RPA 相同的 AES 密钥解开 token 拿到 session id，查 ai_response 表取音频 COS key，签发 1 小时有效的预签名 URL，并收播放埋点。

ap-beijing · /api/audio/play_url · /report_events
独立服务

recommendation_service

独立的 SCF：问题档案匹配、30天排期、到期任务、视频目录同步全部收在这里；MySQL 跟 RPA / audio_analyzation 共用同一个 Tencent CDB 实例，不是独立的库。

ap-beijing · /snapshot · /materialize · /recommend · /due
厂商

DeepSeek API

全链路的 LLM：进程内意图分类、报告口播文案生成、AI Agent2 闲聊都调它；口播这步失败时还有个可配置的备用模型兜底，默认也是 DeepSeek 的另一个模型。

api.deepseek.com/v1 · chat/completions
外部

TTS 服务（第三方本地部署）

由第三方在其自有服务器本地部署、经 ngrok 隧道暴露的语音合成服务。n8n 直接调它，它自己把 wav 写入 COS 并返回 cos_key。

接收报告 token 换取 shortLink，也为每日视频推荐签发小程序深链。

api.people-health.cn

人民健康小程序 / MySQL

shortLink 落地页，用户在这里听语音解读；视频目录主库由 recommendation_service 内部同步。

链路时间线

用户发送 PDF / 图片 / 文本 / 语音

通过企业微信联系人发给 StarBot 机器人。语音也会被转发，但会在 n8n 的 Switch 里被单独分流掉。

StarBot → RPA

事件 POST 到 /api/data，schedule.py 按类型分发。

原始文件上传 COS

PDF/图片先落地对象存储，多页图片会先合并成一份 PDF。

转发给 n8n

sendmsg.py POST 到 n8n cloud 的 /webhook/messages。生产环境 BACKEND_MESSAGES_URL 置空即走这里。

记录用户

n8n 第一步就把 user_id / wechat_name upsert 进 user 表，并刷新最近消息时间。

按消息类型分五路

Switch 的规则是 image / pdf / text / audio，外加一个 fallback。image 与 pdf 会先 Respond to Webhook 给一句回执再继续；text 直接继续、没有回执；audio 与 fallback 直接返回固定话术并结束，根本不进入后续流程。三条继续的路各自把 cos_key 或原文准备好：image 用 {user_id}/image.pdf，pdf 用 {user_id}/pdf-{session_id}.pdf。

意图识别

画布上的 intent-recognition 节点 POST 到 ai_health_report_assistant 自己的 /intent_recognition：文件类消息（pdf/image）按 channel 类型直接判成 medical_report，文本消息交给内部的 DeepSeek 判断。

按意图分三条支路

medical_report 进报告解读；medical_query 回固定婉拒话术；normal_chat 交给 DeepSeek 闲聊 Agent。后两条直接回调 RPA 发文本。

调用 /analyze 做分析

画布上的 体检分析 tecent scf 节点。注意它只传 cos_key 一个字段——上游 prompt 节点拼的那段口播 prompt 并没有发过去，真正用的是 SCF 仓库里自带的提示词。SCF 内部依次跑：识别 → 规则引擎 → 结构化精简 → 口播 LLM，产物写回 COS；推荐快照这一步是一次 POST /snapshot 打到独立的 recommendation_service。最终返回 script 与 layer3_curated。

语音合成

画布上的 语音 节点，把 script 发给第三方本地部署的 TTS（ngrok 隧道）。TTS 自己把 wav 写入 COS，返回 cos_key。

回调 RPA

画布上的 rpa aliyun ecs workbench 节点，POST /api/callback，带 msg_type=tts、音频 cos_key、口播文案、layer3_curated 与 session_id。

人民健康握手

RPA 用 AES 把 session id 加密成 serialized_token，POST /health-reports，再 GET 换取 shortLink。同时把音频 cos_key 写入 ai_response 表。

推送回微信

shortLink 作为文本消息经 StarBot 送达用户。

用户打开小程序

点击 shortLink 落到人民健康小程序，token 随之带入。

换取音频播放地址

小程序拿 token 调 audio scf 的 /api/audio/play_url：解开 token → 查 ai_response 表拿到音频 COS key → 返回 1 小时有效的预签名 URL，用户在此听到解读；播放过程另有埋点上报。

30天推荐编排

回调同时 POST /materialize 到独立的 recommendation_service：它读 COS 上的 profile/coverage 编出 30 天计划，写进自己的 MySQL 与 COS。此后每日 08:30，daily_push.py POST /due 轮询到期任务再推送视频推荐。
