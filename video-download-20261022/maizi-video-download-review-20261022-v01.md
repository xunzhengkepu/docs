# 微信视频下载问题复盘与改进方案

2026年10月22日 · v01

目标：群里收到视频后，系统能自行下载、验证并入库，普通失败能自行恢复，不依赖员工逐条点击微信。

本轮确认的主要问题在程序：文件已经存在却被误报、暂时读不到来源被当成永久冲突，以及入库暂时失败后没有再校验。对应修复已完成；微信最终网络失败码、常规全量对账和异常提醒仍是待实施项。

## 当前已经实施的规则

- 按消息UID、群、发送时间、本地ID和服务端ID核对来源，再判断是不是已有本地文件。文件名来自准确消息的 packed_info_data 视频元数据，不能靠文件名相似或时长相同猜测。
- 存在准确本地引用时核对文件位置、写入稳定性、视频类型和消息时长；否则要求大小和消息MD5一致。PostgreSQL入库独立重读准确消息验证，不能让报告自己声明身份就绕过校验。
- 文件至少稳定3秒；识别本地文件后才登记下载完成。下载完成不直接推进业务task状态，后续文稿匹配和身份规则另行判断。
- 首次加3次自动重试，最多4次。原生请求超过15分钟仍未通过文件核验，记为本系统超时；依次退避1分钟、5分钟、15分钟。该15分钟不是微信视频的保留期限。
- 同一消息使用持久化尝试编号与文件锁；完成登记共用该锁。原生请求使用共享锁，成功卸载后至少间隔30秒。进程重启不重复提交结果未知的尝试。
- 明确来源错误和真实冲突不盲目重试；撤回停止请求。活动原生操作、卸载不确定、崩溃后结果未知时保留证据并拦截，不能删锁后无限重放。
- 每次尝试保留开始、阶段、结果、原生日志及完成记录；成功后的当前错误字段清理，历史错误不删除。日志不记录CDN凭据、AES密钥、密码或完整敏感XML。
- 现有worker有文件事件、下载等待期短间隔检查和每分钟恢复扫描；这不等于已经部署独立的全量文件与数据库对账，因为成功记录仍可能被快速跳过。

## 以后怎样判定问题已解决

1. 一条视频下载链路完成：来源明确，实际文件存在且稳定，验证通过，完成报告与PostgreSQL一致。若无需主动下载，也应计入消息覆盖率。
2. 可恢复问题：程序在该阶段自动重试，不要求员工点微信；已有文件和已完成阶段不重复执行。
3. 不可恢复来源：例如已撤回且没有本地副本，明确显示原因，不把它计为正在下载。
4. 未知微信错误：保留阶段和准确消息依据，不能猜成过期或网络；接入最终结果后再细分。
5. 发布验证：相关模块测试及 npm run test:video-golden 均通过；真实微信下载与离线测试分开报告，不用语法检查或状态Golden代替实际下载验证。

本轮没有证据支持“微信视频统一只能保存15天”能解释这些案例；本系统15分钟超时与微信服务端保留策略无关。任何平台保留期限都不应由本轮超时现象推断。
