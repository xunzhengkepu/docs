先过这几道判断，才会改状态

  • 知道是谁说的：医生、文案、剪辑或运营的身份必须确定；身份未知不猜。
  • 知道说的是哪个 task：根据文案正文、明确标题或编号、引用消息，以及有限上下文关联。视频不能因为挨着上一篇稿，就直接沿用上一任务。
  • 确定是科普任务：患教、类型未知，目前不走这套简化自动流程。
  • 确定是已经发生的事：“明天发布”“没问题再定时”“发布了吗”都不算完成。
  • 通过状态保护：人工改过的最新状态，以及已发布、暂停、异常、已取消、已下架，不自动推进。

每一步：触发条件与真实实例

以下按业务环节列出；第10项包含“已定时”和“已发布”两个状态。修改是回环，明确的文件或发布事实可以跳步，因此不是固定的十次操作。

步骤与变化当前实际规则真实实例与确定条件
1建 task → 文案待医生确认第一份可识别正式文稿建 task。同一医生范围内，正文相似度唯一达到80%的 task 接收修订稿；文件摘要不作业务去重。真实实例 M197310：《盘点五大健康智商税》曾沿用前一秒 M197309 的他汀任务。本轮已拆成独立 task，恢复他汀当前稿，修正 M197318 引用，解除 M197312 普通致谢的单任务关联。两个文稿任务均为文案待医生确认，类型均未明确。
2文案待医生确认／待录制 → 文案修改中医生明确要求修改文案。只记录“在修改”，不要求提取具体意见；文案修改中继续收到修改意见，不会重复产生状态变化。触发条件是已关联到唯一任务的医生修改要求；没有唯一任务关联则不推进。当前规则不从剪辑阶段自动退回文案修改中。未列出未经核实的误更新事故。
3文案修改中 → 文案待医生确认文案人员重新提交修订稿，并且确认属于原 task，重新等待医生确认。修订稿必须归属原 task。此处的状态变化只适用于文案修改中；收到附件本身不等于医生确认。
4文案待医生确认／文案修改中 → 待录制医生对唯一 task 明确说“可以”“没问题”等，结合当前阶段判作文案确认。当前支持 task 级确认，不要求先选文件版本。此前 M204710“可以没问题”漏判已修复；没有把普通“可以”误判的推测列为已发生问题。
5文案阶段 → 待剪辑医生原片已下载、校验成功，时长严格大于2分30秒，转写与文稿唯一匹配。可以从文案待医生确认、文案修改中或待录制进入；不再等“录完了”“发齐了”。文件必须已下载并通过校验；时长大于150秒；转写与唯一任务文稿匹配至少80%。任何一项不满足均不自动进入待剪辑。
6待剪辑 → 剪辑中已确认身份的剪辑师明确说“开始剪”“正在剪”。没有这句话，也允许后面直接通过成片交付推进。必须有已确认剪辑身份、唯一任务与明确开剪陈述。没有开剪消息时不补造剪辑中历史；后续核验成片可直接进入成片待确认。
7交付成片 → 成片待医生确认剪辑师交付的成片已下载，并通过文稿内容匹配。允许从文案阶段、待剪辑、剪辑中或成片修改中进入，跳过缺失的中间消息。只说“剪好了”但没有核验到对应成片，不算。真实实例 M203785：134.862秒视频被150秒门槛排除。已纠正等待分类，登记为范围外证据并提示人工核对。150秒门槛没有修改。
8成片待医生确认／待发布 → 成片修改中医生明确提出修改、补录、换素材等要求。只记录正在修改，不细分修改内容；成片修改中再次收到修改意见，维持原状态。当前自动允许的来源为成片待医生确认、待发布。已定时后的修改要求不会自动撤销平台定时，也不会自动回退本地状态。
9成片待医生确认／成片修改中 → 待发布医生对当前 task 明确说“可以”“发吧”“可以发布”等。不要求先选某个视频版本。医生明确认可且唯一关联到 task 才推进。M197999“用这个1.05倍的，谢谢”只是选版，本轮仅修复归属并登记版本，任务仍为成片待医生确认。
10完成定时 → 已定时；发布事实 → 已发布剪辑或运营明确完成定时、身份和 task 已确认，可从未受保护的前置状态进入已定时。明确平台发布陈述可跳步进入已发布；发文件、发资料、发到群里不算。单说“我发了”且缺少发布语境时待核对。真实实例 M204712“帮您定时啦”已生效为已定时。“我发了文件到群里”误提已发布属于离线规则复现，已修复；没有把它写成生产误发布事故。当前没有平台发布回执。

视频怎么和文稿对应

  1. 先确认文件已下载、可校验，并且视频时长严格大于150秒。当前原片、成片都受此限制。短成片不自动审核，交接视频均已下载且处于该范围时，明确归为范围外证据并提示人工核对。
  2. 先转写0—20秒。有效文字不足40字，就继续转写20—40秒、40—60秒等连续片段，最多累计前120秒。有效文字按代码规范化字符计算，空格和标点不计。
  3. 累计达到40字后尝试匹配；未找到唯一达标 task 时继续每20秒补转，最多前120秒。唯一 task 达到80%即停止；到上限仍不足或不唯一则待核对。
  4. 与文稿正文比较，匹配分数至少80%。这是文字相似度，不是80%的正确概率。
  5. 同一 task 的不同文稿合并成一个候选，取最高分；只有一个不同 task 达到80%才自动关联。两个不同 task 达标仍待核对，也不再要求15个百分点的分差。

这一环的局限

  • 当前候选来自同群、视频消息时间之前且可读取的文稿。候选不存在时，转写成功也不能完成自动匹配。
  • M197761 已由后台完成前120秒转写，口播明确包含“量血压常犯的十个错误”；自动匹配候选仍为0。本轮依据原生引用、口播标题及 M197764 已生效的交付记录，完成有审计记录的归属修复，没有伪造自动匹配成功。
  • 80%是文字相似度阈值，不是正确概率。Golden 与模块测试使用离线证据，不代表真实ASR准确率评测。

每一步怎么留下记录

  • 每次真正生效的状态改变，都在同一个数据库事务里修改 tasks.status、递增 tasks.status_version，并追加 status_history。任何一步失败，整次事务回滚。
  • 自动变化保留来源消息 UID；人工变化保留操作人。最新状态按任务内版本号判断，不能靠 UUID 大小或相同时间戳排序。
  • 同一任务、同一已生效消息重复处理，不重复追加状态历史；旧消息补采、并发版本冲突、人工保护都可能阻止更新。
  • 跳步只记录实际发生的一次变化，例如“文案待医生确认 → 待剪辑”，不伪造中间的文案审批记录。
  • 下载失败、转写失败、匹配不唯一等保存在处理记录里，不冒充业务状态，也不等于业务完成。
