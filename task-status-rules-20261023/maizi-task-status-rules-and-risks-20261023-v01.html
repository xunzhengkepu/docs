先过这几道判断，才会改状态

  • 知道是谁说的：医生、文案、剪辑或运营的身份必须确定；身份未知不猜。
  • 知道说的是哪个 task：根据文案正文、明确标题或编号、引用消息，以及有限上下文关联。视频不能因为挨着上一篇稿，就直接沿用上一任务。
  • 确定是科普任务：患教、类型未知，目前不走这套简化自动流程。
  • 确定是已经发生的事：“明天发布”“没问题再定时”“发布了吗”都不算完成。
  • 通过状态保护：人工改过的最新状态，以及已发布、暂停、异常、已取消、已下架，不自动推进。

每一步：怎么推进，哪里可能出错

以下按业务环节列出；第10项包含“已定时”和“已发布”两个状态。修改是回环，明确的文件或发布事实可以跳步，因此不是固定的十次操作。

步骤与变化当前实际规则潜在问题
1建 task → 文案待医生确认第一份可识别正式文稿即建 task。同一医生范围内按规范化正文相似度比较，唯一 task 达到80%时归入原 task；标题改动或相似修订不另建。文件摘要不作业务去重。【真实遗留】M197310 的《健康智商税》曾错误挂到他汀任务，本轮只读复核仍存在；需要独立核对来源、状态和人工操作后纠正。【确定限制】正文缺失、低于40个有效字符不能识别；同医生多个 task 达标仍待核对。
2文案待医生确认／待录制 → 文案修改中医生明确要求修改文案。只记录“在修改”，不要求提取具体意见；文案修改中继续收到修改意见，不会重复产生状态变化。【代码边界／预判风险】“这里改一下”可能不知道指哪篇；修改关键词识别不全会漏判。剪辑已经开始以后，再改文案，目前不会自动退回文案修改中。
3文案修改中 → 文案待医生确认文案人员重新提交修订稿，并且确认属于原 task，重新等待医生确认。【代码边界／预判风险】修订稿如果没关联上原 task，可能变成新任务或待核对。其他阶段收到新稿，不一定自动回到文案待确认；登记文件与改变状态是两回事。
4文案待医生确认／文案修改中 → 待录制医生对唯一 task 明确说“可以”“没问题”等，结合当前阶段判作文案确认。【预判风险，未确认生产误更新】普通应答“可以”在唯一待确认任务上下文中可能被当成审核。本轮保留已确认的 task 级审核规则，不强制选择文件版本；关联和对话意图仍需进一步加强。
5文案阶段 → 待剪辑医生原片已下载、校验成功，时长严格大于2分30秒，转写与文稿唯一匹配。可以从文案待医生确认、文案修改中或待录制进入；不再等“录完了”“发齐了”。【真实出现过的下载与匹配阻塞；其余为规则局限】下载失败、文稿缺失、转写不准、多个 task 达标都会卡住。2分30秒及以下的正式原片也会被过滤。旧片重发可能仍匹配；匹配本身不证明拍摄时间或录制质量。
6待剪辑 → 剪辑中已确认身份的剪辑师明确说“开始剪”“正在剪”。没有这句话，也允许后面直接通过成片交付推进。【信息局限／预判风险】剪辑师没在群里说，状态可能一直显示待剪辑，不一定代表实际没开剪。替人转述、多个任务并行时，也可能难以关联。
7交付成片 → 成片待医生确认剪辑师交付的成片已下载，并通过文稿内容匹配。允许从文案阶段、待剪辑、剪辑中或成片修改中进入，跳过缺失的中间消息。只说“剪好了”但没有核验到对应成片，不算。【真实发生】M203785 对应134.862秒成片，被150秒门槛排除却仍等待匹配。【本轮已修】当本次交接的所有视频均已下载且不超过150秒，记录为范围外证据、提示人工核对，不再冒充等待ASR；混合长短视频不整体关闭。【仍保留】150秒门槛、代发身份核实、待发布或已定时后新成片不自动重新送审。
8成片待医生确认／待发布 → 成片修改中医生明确提出修改、补录、换素材等要求。只记录正在修改，不细分修改内容；成片修改中再次收到修改意见，维持原状态。【保护规则／预判风险】指代不清会关联错；“其他没问题”不能当整体通过。已定时后再提出修改，目前不会自动转回修改中，需要人工处理，也不会自动撤销平台定时。
9成片待医生确认／成片修改中 → 待发布医生对当前 task 明确说“可以”“发吧”“可以发布”等。不要求先选某个视频版本。【预判风险，未确认生产误更新】可能把针对旧片、素材或其他事情的“可以”当成通过。如果一个 task 里存在差异很大的视频版本，task 层面的确认不能保证最后发布文件正确。
10完成定时 → 已定时；发布事实 → 已发布剪辑或运营明确完成定时、身份和 task 已确认，可从未受保护的前置状态进入已定时。明确平台发布陈述可跳步进入已发布；发文件、发资料、发到群里不算。单说“我发了”且缺少发布语境时待核对。【真实发生、此前已修】M204710“可以没问题”漏判、M204712定时跳步被拒；本轮只读确认 M204712 已生效为已定时。【本轮规则层复现并修复】“我发了文件到群里”“我发了参考资料”曾提出已发布，现转待核对；这不等于发现生产库误发布实例。【信息局限】仍没有平台回执，无法仅凭聊天知道定时后来是否取消或发布失败。

视频怎么和文稿对应

  1. 先确认文件已下载、可校验，并且视频时长严格大于150秒。当前原片、成片都受此限制。短成片不自动审核，交接视频均已下载且处于该范围时，明确归为范围外证据并提示人工核对。
  2. 先转写0—20秒。有效文字不足40字，就继续转写20—40秒、40—60秒等连续片段，最多累计前120秒。有效文字按代码规范化字符计算，空格和标点不计。
  3. 累计达到40字后尝试匹配；未找到唯一达标 task 时继续每20秒补转，最多前120秒。唯一 task 达到80%即停止；到上限仍不足或不唯一则待核对。
  4. 与文稿正文比较，匹配分数至少80%。这是文字相似度，不是80%的正确概率。
  5. 同一 task 的不同文稿合并成一个候选，取最高分；只有一个不同 task 达到80%才自动关联。两个不同 task 达标仍待核对，也不再要求15个百分点的分差。

这一环的局限

  • 【此前已修】“够40字但匹配失败不继续补转”已不符合当前实现；当前支持继续补转。离线分段测试不等于真实ASR准确率评测。
  • 当前匹配查找同群、视频消息时间之前的文稿；文稿后来才发或只在其他群，可能找不到。
  • 口误、方言、背景音、转写错误、临场改词会降低分数；多篇稿开头相似，也可能导致多个任务达标。当前不是完整视频语义理解。

贯穿整个流程的问题

人工修改保护

【确定的保护规则】最新一条状态历史如果是人工修改，后续自动变更会被拦截。人工更正以后，还需要明确如何恢复自动处理，不能假设下一条聊天会自动接着跑。

纠正视频关联不会自动回退原任务

【代码边界／待完善】视频自动挂错 task 后可以按新证据纠正，但原 task 之前被错误推进的进度不会自动撤销，可能需要单独核对。人工确认过的关联、人工状态和已用于发布的视频受保护。

已发布后的返工与下架

【确定的保护规则】当前已发布会停止自动推进；后续返工、撤回、下架等需要人工处理。暂停、异常、已取消、已下架也不会自动恢复。

阿里云盘第二入口

【代码边界／待完善】少量医生通过阿里云盘链接上传视频的功能继续保留。现有专用入口能下载视频和文稿、生成候选证据，但尚未完整接入统一 task 自动匹配与失败提醒台账。“发了云盘链接”或“已上传”不能直接替代视频证据。

聊天事实与平台事实有差距

【代码边界／待完善】目前主要依据可关联的聊天和文件证据推进，不等于自动登录发布平台核验。员工完成定时但没说，或说了之后又取消，都可能造成状态与实际操作不一致。

原生引用选片遗漏识别入口

【真实发生】历史审计 E046／M197999 已定位308.417秒视频，但版本选择事件没进入识别队列。【本轮已修入口】待核对版本选择也进入队列，仅接受同群且原生引用已验证的视频；无引用、未经验证或跨群均不按邻近视频猜测。修复入口不保证该历史作品立即闭环，仍受身份、文稿、匹配和类型条件约束。

每一步怎么留下记录

  • 每次真正生效的状态改变，都在同一个数据库事务里修改 tasks.status、递增 tasks.status_version，并追加 status_history。任何一步失败，整次事务回滚。
  • 自动变化保留来源消息 UID；人工变化保留操作人。最新状态按任务内版本号判断，不能靠 UUID 大小或相同时间戳排序。
  • 同一任务、同一已生效消息重复处理，不重复追加状态历史；旧消息补采、并发版本冲突、人工保护都可能阻止更新。
  • 跳步只记录实际发生的一次变化，例如“文案待医生确认 → 待剪辑”，不伪造中间的文案审批记录。
  • 下载失败、转写失败、匹配不唯一等保存在处理记录里，不冒充业务状态，也不等于业务完成。
