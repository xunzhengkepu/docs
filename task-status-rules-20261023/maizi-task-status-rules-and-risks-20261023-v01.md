# 当前 task 状态转换：每一步的规则与潜在问题

2026-10-23 · v01

10个主流程状态，按已经发生的事实推进，允许跳步。本次仅发布文档，不修改代码、数据库或配置。以下问题不代表已经修复。

## 共同前提

- 知道是谁说的：医生、文案、剪辑或运营的身份必须确定；身份未知不猜。
- 知道说的是哪个 task：根据文案正文、明确标题或编号、引用消息，以及有限上下文关联。视频不能因为挨着上一篇稿，就直接沿用上一任务。
- 确定是科普任务：患教、类型未知，目前不走这套简化自动流程。
- 确定是已经发生的事：“明天发布”“没问题再定时”“发布了吗”都不算完成。
- 通过状态保护：人工改过的最新状态，以及已发布、暂停、异常、已取消、已下架，不自动推进。

## 每一步的规则与问题

### 1. 建 task → 文案待医生确认

当前规则：读到正式文案，能够识别标题和正文后建 task。同一医生、相同规范化正文继续用原 task，改名或重发不另建。

潜在问题：文件没下载、正文读不到，就可能建不了。正文修改后要靠原 task、标题或引用关联；同名不同内容、重复旧任务可能产生冲突。文稿解析目前要求至少40个有效字符。

### 2. 文案待医生确认／待录制 → 文案修改中

当前规则：医生明确要求修改文案。只记录“在修改”，不要求提取具体意见；文案修改中继续收到修改意见，不会重复产生状态变化。

潜在问题：“这里改一下”可能不知道指哪篇；修改关键词识别不全会漏判。剪辑已经开始以后，再改文案，目前不会自动退回文案修改中。

### 3. 文案修改中 → 文案待医生确认

当前规则：文案人员重新提交修订稿，并且确认属于原 task，重新等待医生确认。

潜在问题：修订稿如果没关联上原 task，可能变成新任务或待核对。其他阶段收到新稿，不一定自动回到文案待确认；登记文件与改变状态是两回事。

### 4. 文案待医生确认／文案修改中 → 待录制

当前规则：医生对唯一 task 明确说“可以”“没问题”等，结合当前阶段判作文案确认。

潜在问题：“可以”也可能只是答应其他事情。当前不要求明确引用某一版文稿；最近上下文只出现一个待确认任务，也可能被关联，因此仍有误把普通回复当审核通过的风险。

### 5. 文案阶段 → 待剪辑

当前规则：医生原片已下载、校验成功，时长严格大于2分30秒，转写与文稿唯一匹配。可以从文案待医生确认、文案修改中或待录制进入；不再等“录完了”“发齐了”。

潜在问题：下载失败、文稿缺失、转写不准、多个 task 达标都会卡住。2分30秒及以下的正式原片也会被过滤。旧片重发可能仍匹配；匹配本身不证明拍摄时间或录制质量。

### 6. 待剪辑 → 剪辑中

当前规则：已确认身份的剪辑师明确说“开始剪”“正在剪”。没有这句话，也允许后面直接通过成片交付推进。

潜在问题：剪辑师没在群里说，状态可能一直显示待剪辑，不一定代表实际没开剪。替人转述、多个任务并行时，也可能难以关联。

### 7. 交付成片 → 成片待医生确认

当前规则：剪辑师交付的成片已下载，并通过文稿内容匹配。允许从文案阶段、待剪辑、剪辑中或成片修改中进入，跳过缺失的中间消息。只说“剪好了”但没有核验到对应成片，不算。

潜在问题：当前成片也受“严格超过2分30秒”限制，较短的正常成片会被挡住。他人代发、开头改动较大、视频与交付消息没关联，也可能识别不了。待发布或已定时后出现新成片，目前不能自动重新送审。

### 8. 成片待医生确认／待发布 → 成片修改中

当前规则：医生明确提出修改、补录、换素材等要求。只记录正在修改，不细分修改内容；成片修改中再次收到修改意见，维持原状态。

潜在问题：指代不清会关联错；“其他没问题”不能当整体通过。已定时后再提出修改，目前不会自动转回修改中，需要人工处理，也不会自动撤销平台定时。

### 9. 成片待医生确认／成片修改中 → 待发布

当前规则：医生对当前 task 明确说“可以”“发吧”“可以发布”等。不要求先选某个视频版本。

潜在问题：可能把针对旧片、素材或其他事情的“可以”当成通过。如果一个 task 里存在差异很大的视频版本，task 层面的确认不能保证最后发布文件正确。

### 10. 待发布 → 已定时；发布事实 → 已发布

当前规则：剪辑或运营明确说“帮您定时啦”“已设置定时”，从待发布进入已定时。医生、剪辑或运营明确陈述已发布且能对应 task，可从其他未受保护状态直接进入已发布，不补造中间审批。

潜在问题：定时可能被取消或发布失败；时间到了不会自动变已发布。缺少前面确认消息、状态不是待发布时，定时消息可能卡住。“我发了”可能只是发到群里，存在被误判成平台发布的风险。

## 视频匹配

1. 先确认文件已下载、可校验，并且视频时长严格大于150秒。当前原片、成片都受此限制。
2. 先转写0—20秒。有效文字不足40字，就继续转写20—40秒、40—60秒等连续片段，最多累计前120秒。有效文字按代码规范化字符计算，空格和标点不计。
3. 达到40字后停止补转；到上限仍不足40字则待核对。40字现在是补转停止条件与不足文本保护，不是以前“前20秒不够40字就直接放弃”的做法。
4. 与文稿正文比较，匹配分数至少80%。这是文字相似度，不是80%的正确概率。
5. 同一 task 的不同文稿合并成一个候选，取最高分；只有一个不同 task 达到80%才自动关联。两个不同 task 达标仍待核对，也不再要求15个百分点的分差。

局限：

- 已经够40字、但分数不到80%时，当前不会仅因为匹配失败就继续多转20秒。
- 当前匹配查找同群、视频消息时间之前的文稿；文稿后来才发或只在其他群，可能找不到。
- 口误、方言、背景音、转写错误、临场改词会降低分数；多篇稿开头相似，也可能导致多个任务达标。当前不是完整视频语义理解。

## 贯穿流程的问题

### 人工修改保护

最新一条状态历史如果是人工修改，后续自动变更会被拦截。人工更正以后，还需要明确如何恢复自动处理，不能假设下一条聊天会自动接着跑。

### 纠正视频关联不会自动回退原任务

视频自动挂错 task 后可以按新证据纠正，但原 task 之前被错误推进的进度不会自动撤销，可能需要单独核对。人工确认过的关联、人工状态和已用于发布的视频受保护。

### 已发布后的返工与下架

当前已发布会停止自动推进；后续返工、撤回、下架等需要人工处理。暂停、异常、已取消、已下架也不会自动恢复。

### 阿里云盘第二入口

少量医生通过阿里云盘链接上传视频的功能继续保留。现有专用入口能下载视频和文稿、生成候选证据，但尚未完整接入统一 task 自动匹配与失败提醒台账。“发了云盘链接”或“已上传”不能直接替代视频证据。

### 聊天事实与平台事实有差距

目前主要依据可关联的聊天和文件证据推进，不等于自动登录发布平台核验。员工完成定时但没说，或说了之后又取消，都可能造成状态与实际操作不一致。

## 状态历史

- 每次真正生效的状态改变，都在同一个数据库事务里修改 tasks.status、递增 tasks.status_version，并追加 status_history。任何一步失败，整次事务回滚。
- 自动变化保留来源消息 UID；人工变化保留操作人。最新状态按任务内版本号判断，不能靠 UUID 大小或相同时间戳排序。
- 同一任务、同一已生效消息重复处理，不重复追加状态历史；旧消息补采、并发版本冲突、人工保护都可能阻止更新。
- 跳步只记录实际发生的一次变化，例如“文案待医生确认 → 待剪辑”，不伪造中间的文案审批记录。
- 下载失败、转写失败、匹配不唯一等保存在处理记录里，不冒充业务状态，也不等于业务完成。
