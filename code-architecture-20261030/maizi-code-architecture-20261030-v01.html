科普麦子：项目结构图与技术选型

员工在网页工作；这台 Windows 电脑负责接入微信、处理本地媒体和推进作品；阿里云负责网页服务与查询副本。下面逐步解释：数据从哪里来、经过什么程序、为什么用这些技术。

先分清三件事当前业务主库是本机 PostgreSQL；云端网页查询自己的SQLite 消息副本；ECS 上另有PostgreSQL 单向业务镜像。这三个库不是同一个用途，也不是两个业务主库同时写。

核对依据：2026-10-30 本机源码、已启用配置、管理脚本与现有部署说明。本文说明结构，不是“所有附件成功”或“DLL 稳定”的验收结论。仅发布文档，不部署业务程序。

总体结构四条主链路逐步技术选型进程与锁数据放在哪里边界与测试

总体结构：本机、阿里云、外部服务

这不是“后端全部在阿里云”，也不是“网页直接控制员工电脑”。本机程序主动向云端同步消息、领取发送任务并上传预览。原件主要留本机；Qwen 和飞书分别承担模型处理与协作同步。

wx-cli 读取微信数据，与我们用于发送／主动下载的 C++ 原生适配器是不同依赖。企微旧系统、历史分析脚本和早期 FastAPI 原型不计入这张当前运行主链路图。

先沿四条业务链路理解

A. 客户发消息 → 员工看见

微信收到 → 采集器读取 → 本机 SQLite 归档 → HTTPS 增量同步 → 云端 SQLite → SSE 提醒浏览器重新查询。图片或转写较慢时，不要求文字消息一起等待。

B. 客户发附件 → 网页能预览

归档只证明“收到一条附件消息”，不证明文件已下载。先查本机源文件；确需主动下载时提交微信，外部核验落盘，再生成预览并上传云端。缩略图、普通清晰图、原图与原视频分别标记。

C. 员工点击发送 → 微信发出

网页保存发送任务 → 本机领取 → 账号／版本／上下文校验 → 原生发送 → 持久化回执并回传。结果未知时保留核对入口，不因一次超时就重复发给客户。

D. 群聊证据 → 作品进度 → 飞书

归档唤醒状态 worker → 身份与唯一 task 关联 → 文档／视频证据、Qwen 语义候选和规则校验 → 本机 PostgreSQL 事务提交 → 创建或更新飞书 → 回读核对。无法确定任务或遇到人工冲突，进入待核对。

每一步使用什么技术，为什么这样用

下面的“为什么”说明这套组合的作用与代价；不表示每项都是永远最优的选型。

01

微信客户端：消息和媒体的源头

Windows 微信客户端、本地消息数据库与媒体文件

这一步做什么
客户发文字、图片、视频或文档，先由微信接收。程序从本机记录读取证据；真正发送和客户端原生下载仍由已登录微信执行。
为什么用这套技术
现有接入能力依赖这台电脑的微信进程和本地数据，因此微信相关工作放在 Windows 附近。把网页移到云端，并不能把这部分依赖消掉。
代价与边界
微信离线、账号退出、资源撤回或消息缓存不可读时，下游不能凭空恢复附件。

代码：tools/chat-viewer/wx-reader.mjs · tools/chat-viewer/verify-wechat-process.py

02

采集：发现变化后读取并规范化

Node.js 文件通知、wx-cli、JSON、恢复检查

这一步做什么
文件变化触发采集，wx-cli 读取会话／历史，Node.js 规范化并导入归档。恢复检查补漏；文件通知只是唤醒信号，不是完整消息本身。
为什么用这套技术
Node.js 适合文件事件、子进程和 I/O 调度；复用 wx-cli 读取能力，避免另写一套完整的微信数据读取工具。
代价与边界
wx-cli 是第三方依赖；缓存刷新与读取不是同一个事务，仍可能遇到短暂不可读。不能把“读不到”自动解释为“已撤回”。

代码：tools/chat-viewer/refresh.mjs · tools/chat-viewer/sync.mjs · tools/chat-viewer/message-cache.py

03

本机消息归档：留下稳定的证据

SQLite、Node 内置 SQLite、FTS、稳定消息 UID、增量游标

这一步做什么
归档消息、会话、来源与媒体索引，依靠消息身份去重。提交后写唤醒信号，供同步和作品状态消费；失败可从已保存的游标接续。
为什么用这套技术
SQLite 无需额外数据库服务，适合单机归档、搜索与可搬运快照。消息归档与后面的业务 PostgreSQL 分工不同。
代价与边界
SQLite 归档与 PostgreSQL 业务库不构成跨库事务；靠 UID、游标、幂等和核对衔接。

代码：tools/chat-viewer/db.mjs · tools/chat-viewer/import.mjs

04

云端同步：消息先到，媒体后补

Node.js、HTTPS、确认游标、异步任务

这一步做什么
cloud-sync 向云端上传增量消息和必要映射。图片、语音、视频、文档各有异步处理入口，媒体较慢时文字同步继续；云端确认后才前移同步位置。
为什么用这套技术
本机主动向外发 HTTPS 请求，员工不必直接连接这台电脑。消息通道与重任务解耦，网络恢复后能够接续。
代价与边界
这是最终一致：文字可能先出现，预览随后补上。部分媒体同步共用 cloud-sync 进程，并非每种附件都有独立常驻进程。

代码：tools/chat-viewer/cloud-sync.mjs · tools/chat-viewer/cloud-store.mjs

05

员工网页：登录、搜索、浏览和操作

Nginx、Node.js HTTP、HTML/CSS/原生 JavaScript、SSE

这一步做什么
Nginx 负责 HTTPS 和反向代理；Node 服务做鉴权、查询与固定业务 API。浏览器通过 SSE 收到“数据已变化”的通知后再请求增量；媒体从云端缓存读取。
为什么用这套技术
当前页面需求可由原生前端和 Node HTTP 完成，依赖较少。SSE 满足服务器通知浏览器更新的需求；发送操作另走普通 HTTP。
代价与边界
当前主链路不是 React/Vue 前端，也不是早期 app/ 中的 FastAPI 服务。云端能提供已同步历史，但本机离线后新消息与真实发送会受影响。

代码：tools/chat-viewer/server.mjs · tools/chat-viewer/public/app.js · tools/chat-viewer/archive-events.mjs

06

原生提交：协调发送和主动下载

Node 调度、Python 准备、C++ DLL、PowerShell、互斥与版本／哈希校验

这一步做什么
普通图／原图选择对应资源；需要主动下载时提交给微信。图片与视频协调原生操作机会，并照顾发送优先；生命周期条件满足且核实模块退出后才释放。
为什么用这套技术
现有功能调用微信进程内的能力，C++ 承担原生桥接；Node/Python 负责外围队列、身份、资源准备和记录。短时提交减少驻留范围。
代价与边界
短时加载不等于绝对安全。内部 ABI、回调生命周期、微信版本与账号验证仍是风险；结果不明不自动删除阻断或重复执行。

代码：tools/chat-viewer/native-send.mjs · tools/chat-viewer/image-resource-contract.py · tools/chat-viewer/native-send/

07

媒体完成：验证文件，再生成网页预览

独立 observer、Python、MD5/SHA-256、Pillow／AES、FFmpeg/FFprobe、SILK WASM

这一步做什么
外部观察精确消息与本地文件，完整性通过后核销旧失败。图片生成清晰预览；视频生成压缩 MP4；语音解码为可播放格式；Office/PDF 等生成受限正文预览。实际上传后云端才标记 ready。
为什么用这套技术
文件与媒体库放在 Python／专门工具中更自然；压缩预览上云降低传输和云盘成本。外部观测不增加微信内部回调，也不需要一直占用原生操作锁。
代价与边界
缩略图不等于原图，预览不等于原件。转换使用受限子进程／队列，并非全部并发。撤回、缺失与不可验证资源不能改成成功。

代码：tools/chat-viewer/media-observer-worker.mjs · tools/chat-viewer/observe-media.py · tools/chat-viewer/prepare-video-preview.py · tools/chat-viewer/voice-sync.mjs

08

语音和语义：两种不同的 Qwen 工作

Qwen ASR（默认 qwen3-asr-flash）、Qwen Plus、Python HTTP／结构校验

这一步做什么
语音消息与视频音轨先转成受限 WAV，再调用 ASR 得到文本。作品状态另由 Qwen Plus 生成结构化语义候选，再结合身份、任务、版本和业务规则校验。当前本机语义配置为 apply。
为什么用这套技术
托管 ASR 减轻本机模型推理负担；共用适配器与音频指纹便于复用结果。模型擅长理解表达，规则与数据库负责可验证的状态约束。
代价与边界
依赖网络、费用与第三方音频处理。Whisper 仍有历史／可选代码，不应把它当作当前 Qwen 配置下的默认路径。转写正确不等于任务匹配或审批判断正确。

代码：tools/chat-viewer/qwen-asr.py · tools/video-pilot/qwen_state.py · tools/video-pilot/workflow_media.py

09

员工发送：保存任务后由本机执行

云端 SQLite outbox、领取凭据、本机 JSON 回执、Node send-worker、原生适配

这一步做什么
网页先把发送请求写入云端队列。本机主动领取，校验微信身份与上下文，准备附件后执行原生发送，再保存并回传结果。已发送但回执未确认与完全未发送必须区分。
为什么用这套技术
请求和执行分离，员工浏览器不必等微信内部调用结束；持久化回执支持重启后核对，不把网络请求成功误当成消息发送成功。
代价与边界
结果未知时暂停并核对，不盲目重发。单个微信账号的原生操作仍需串行协调；增加网页用户不会让同一个微信进程无限并发。

代码：tools/chat-viewer/outbox.mjs · tools/chat-viewer/send-worker.mjs · tools/chat-viewer/native-send.mjs

10

作品状态：本机 PostgreSQL 事务是业务依据

Node 常驻 worker、Python 状态机、PostgreSQL、psycopg、行锁／CAS／事务 outbox

这一步做什么
读取归档消息，确定身份和唯一作品，结合当前稿件／成片证据判断状态。在同一业务事务内提交任务、历史、版本、消费位置与待同步记录；媒体证据另有独立 worker。
为什么用这套技术
PostgreSQL 适合多表关联、约束、并发控制与追加历史；状态、历史与 outbox 同事务，避免只改状态却丢了同步任务。Node 负责唤醒，Python 复用规则与媒体生态。
代价与边界
证据不足进入待核对，不能凭“可以”猜任务。当前配置连接本机 PostgreSQL；云端有同名副本不代表已切主。

代码：tools/chat-viewer/task-state-worker.mjs · tools/chat-viewer/media-evidence-worker.mjs · tools/video-pilot/live_state.py · tools/video-pilot/postgres_state_store.py

11

飞书：把业务结果同步给协作表格

飞书 API／CLI、创建 journal、稳定 task ID、非空校验、回读确认

这一步做什么
本机任务先成立，再由同步逻辑创建／绑定飞书行并更新进度。标题不能为空，同 task 通过稳定绑定与创建记录防止重试重复建行；更新后回读，人工冲突保留待核对。
为什么用这套技术
把飞书作为协作界面和同步目标，远端暂时不可用时仍可保留本机任务。创建 journal 与 outbox 留下可追溯的同步过程。
代价与边界
本机数据库和飞书之间没有一个共同事务；不能承诺端到端 exactly-once，也不能宣称绝无语义重复。并发人工修改仍要处理冲突。

代码：tools/video-pilot/feishu_task_create.py · tools/video-pilot/feishu_state_pilot.py · tools/video-pilot/live_state.py

12

云端业务副本、运维与测试

Python/psycopg 一致快照、HTTPS、PostgreSQL 镜像；PowerShell/计划任务；systemd；GitHub Actions

这一步做什么
本机约每 60 秒读取一致业务快照，经 HTTPS 同步到 ECS 副本并核对指纹。Windows 管理脚本负责进程启动／恢复，云端由 systemd 等管理。CI 执行固定回归和临时 PostgreSQL 测试。
为什么用这套技术
先保留单一业务写入端，避免双主冲突；现有镜像能支持云端查询与核对。多进程便于按职责重启与设置超时，CI 保留已确认业务规则。
代价与边界
快照镜像不是 WAL 流复制、自动切主或完整灾备。进程心跳正常不等于任务成功；自动巡检也不等于所有失败都能自动修复。

代码：tools/video-pilot/business_mirror.py · tools/video-pilot/business_mirror_receiver.py · tools/chat-viewer/manage.ps1 · .github/workflows/video-golden.yml

后台到底是多进程，还是多线程？

主体是多个独立进程，加上 Node 异步 I/O、Python／工具子进程；不是一个线程包办全部，也不是每条消息都开一个线程。

组件主要职责隔离与限制
refresh发现变化、采集、归档与媒体识别和发送分开，模型卡住不应让采集等待。
cloud-sync增量消息同步及媒体同步入口不同媒体异步调度，但部分共用这个进程；进程退出会影响这些共用任务。
send-worker领取与执行发送、回传结果持久化 active/result；未知结果阻断重发。与原生下载协调。
video-opening / media-evidence本地视频查找、开头分析、业务媒体证据独立 worker 与受限子进程；不能认为二者对所有视频做相同分析。
media-observer只读检查已有缓存和文件，纠正回执不调用 wx.exe、DLL 或下载接口；无法解释微信 CDN 内部失败原因。
source-ready-sync发现本机新可用源，通知云端重新准备与 observer 的失败核对职责不同；仍须云端实际领取和上传。
task-state消费消息、推进作品、飞书同步主业务事务在本机 PostgreSQL；不能再启动一个云端业务主消费者。
business-mirror本机业务一致快照 → ECS 副本单向同步，目标指纹变化则拒绝覆盖；不是自动故障转移。

需要协调互斥的地方

  • 发送和图片／视频原生操作的机会分配。
  • 同一消息的下载尝试与完成回执更新。
  • 作品状态的版本修改、历史追加与同步出队。

不该长期占原生锁的地方

  • 等待微信网络下载、观察文件落盘。
  • FFmpeg 转码、语音识别和云端上传。
  • 浏览器搜索与读取已有云端预览。

队列繁忙、任务失败、通道阻断和进程退出是不同情况。诊断状态文件写失败要记录并恢复，但不能把一次已完成发送变成新的发送。结果不明的原生操作也不能靠“锁时间到了”强行清除。

数据放在哪里，为什么不是统一一个库？

存储内容与权威范围采用原因 / 代价
微信本地数据库与文件客户端源记录、原生资源引用、媒体原件。源头在本机；存在版本、撤回、缓存更新与可读性边界。
本机 SQLite规范化消息归档与查询索引。部署轻、便于证据回放；不是正式作品状态主库。
本机 PostgreSQLbusiness/workflow：任务、历史、关联、判断、游标、同步队列。事务、外键、行锁与版本约束；本机离线影响业务推进。
云端 SQLite + 文件目录员工可查询的消息副本、发送与媒体任务、预览文件。网页快速服务已同步内容；云端容量与淘汰规则需要持续管理。
云端 PostgreSQL本机业务库的单向表数据镜像。便于云端核对；不是自动切主热备，也不复制全部角色／DDL／媒体。
JSON 回执与心跳本机进程状态、原生尝试、结果与诊断证据。简单可追查；Windows 文件替换需有限重试，不能把它们当成可靠的通用多机队列。

当前没有统一采用 Redis、Celery 或 Kafka。已有队列分别使用 SQLite、PostgreSQL 表及本机回执。减少了常驻依赖，但也增加跨进程状态核对的责任；将来扩容要先识别瓶颈，不能仅增加 worker 数量。

技术选型的收益、限制与验证

画出隔离边界，不等于故障已经清零缓存读取失败可能使程序还未读到撤回状态就报错；原生请求返回也可能始终没有完整文件。需要继续定位来源与完成证据，不能把所有问题都归因于 DLL 或网络。
  • Node.js：适合网页、I/O、事件与队列协调；同步阻塞代码仍会阻塞所属进程，不应把 CPU 重任务直接堆在事件循环。
  • Python：适合媒体、文档、数据库和模型适配；子进程需要超时、输出限制和资源管理。
  • C++ 原生适配：提供当前发送和主动下载能力，也是稳定性最敏感的边界。外围超时与锁修复不证明 DLL 长期稳定。
  • Qwen：减少本机推理负担，但引入 API 成本、网络依赖及音频离机处理。ASR 文本、模型候选与业务事实必须分开。
  • 本地优先：单一业务写入点清楚，依赖当前电脑在线。电脑关闭后，云端可继续提供已有缓存，但不能保证新收发和未准备附件继续完成。
  • 现有镜像：约每分钟同步快照，数据量增大后成本会增长。是否迁移主库、采用增量复制是后续设计，不是当前已完成能力。
